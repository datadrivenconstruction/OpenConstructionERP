## HIGH (10)

### [procurement] Goods-receipt over-receipt: quantity validation is per-GR, never cumulative across receipts
- File: `backend/app/modules/procurement/service.py:1010-1033 (create_goods_receipt) and 1122-1147 (confirm_goods_receipt)`
- What: create_goods_receipt validates each GR item with `received > ordered` comparing ONLY the single line's quantity_received against the PO line's full ordered quantity. It never sums quantity already received on prior (confirmed) GRs for the same po_item_id. So a PO line of 100 can be received via two separate GRs of 100 each (200 received) and both pass. confirm_goods_receipt computes the GR value as `qty * po_item.unit_rate` and publishes `procurement.gr.confirmed` with that amount, so finance flips committed->actual for the inflated quantity, over-stating actual cost. `_check_po_fully_received` only checks `received < ordered`, so over-receipt is silently treated as fully received and the PO is marked completed. There is no DB or service-level cumulative cap.
- Evidence: Validation: `ordered = Decimal(po_item.quantity); received = Decimal(item_data.quantity_received); if received > ordered: raise 400`. No query of GoodsReceiptItem sums for already-received qty before this check; _check_po_fully_received returns False only when `received < ordered` (never flags `>`).
- Fix: Before accepting a GR line, sum quantity_received over existing confirmed GRs for that po_item_id and reject when `already_received + new_received > ordered` (allowing a configurable over-delivery tolerance). Apply the same cumulative cap at confirm time so split receipts cannot exceed the ordered quantity.

### [tendering] apply_winner overwrites arbitrary BOQ Position rows from bid JSON position_id without scoping to the package BOQ (cross-project data corruption)
- File: `backend/app/modules/tendering/service.py:578-597 (apply_winner)`
- What: apply_winner iterates the winning bid's `line_items` (free-form JSON), reads each `position_id`, loads the Position via `self.session.get(Position, pos_uuid)` and overwrites its `unit_rate` and `total`. It never verifies that the resolved Position belongs to `package.boq_id` (or even to the package's project). The router only checks the caller owns the AWARD package's project, not the targeted positions. Because bid line_items are arbitrary JSON a bidder/import can populate, a user who legitimately owns package P in project A can award a bid whose line_items reference position_ids belonging to another project's BOQ, silently rewriting those foreign positions' unit rates and totals. This corrupts another tenant's budget.
- Evidence: `pos = await self.session.get(Position, pos_uuid); if pos is None: continue; qty = _to_decimal(pos.quantity); new_total = qty * rate; await self.session.execute(update(Position).where(Position.id == pos.id).values(unit_rate=str(rate), total=str(new_total)))` - no `pos.boq_id == package.boq_id` guard.
- Fix: After loading each Position, skip (or 400) any whose `boq_id != package.boq_id`. Ideally constrain the UPDATE with `Position.boq_id == package.boq_id` in the WHERE clause so a foreign position_id can never be written.

### [validation] IDS rule import mutates the process-global rule registry with no tenant/project scoping (cross-project rule leak)
- File: `backend/app/modules/validation/router.py:300-349 (esp. 341)`
- What: POST /api/v1/validation/import-ids parses an uploaded IDS file and calls `rule_registry.register(rule, rule_sets=[rule_set, 'IDS'])` for each spec. `rule_registry` is the single process-global singleton (app/core/validation/engine.py:467) that `validation_engine.validate()` consults for EVERY project's /validation/run. The endpoint takes no project_id and performs no _require_project_access. Consequences: (1) Multi-tenant isolation breach - rules uploaded by a user working on project A are applied to validation runs of project B (and every other tenant) because the registry is global and shared. (2) The mutation is not idempotent across the cluster and is lost on restart, so behavior is non-deterministic and depends on which uploads happened to land on a given worker. (3) Any user with the role-level `validation.create` permission can inject arbitrary regex-bearing rules that run against all projects.
- Evidence: Handler signature has no project_id and no `_require_project_access` (contrast every other validation endpoint which calls it). Body: `for rule in rules: rule_registry.register(rule, rule_sets=[rule_set, 'IDS'])`. engine.py: `rule_registry = RuleRegistry(); validation_engine = ValidationEngine(rule_registry)` - one shared instance; ValidationEngine.validate -> registry.get_rules_for_sets(rule_sets) returns whatever was globally registered.
- Fix: Scope imported IDS rules to a project (persist them to a per-project rule table and load them into a request-scoped registry, or namespace the rule_set by project_id and require it as a path/body param gated by _require_project_access). At minimum require project_id + access check and never register into the global singleton that drives all tenants.

### [correspondence] Reference-number generator races and breaks past COR-999 (silent duplicate ref numbers)
- File: `backend/app/modules/correspondence/repository.py:42-52 (next_reference_number); models.py:26 (no unique constraint); service.py:44-64 (create has no retry)`
- What: next_reference_number computes the next number from func.max(Correspondence.reference_number) on a STRING column. Two problems. (1) Lexical MAX on a string is wrong once the count crosses 999: with format COR-%03d the suffix grows to 4 digits, and lexically 'COR-1000' < 'COR-999' (because '1' < '9'), so MAX returns 'COR-999' and the generator emits 'COR-1000' on every subsequent create from then on - a permanent collision/duplicate stream. (2) There is no unique constraint on (project_id, reference_number) (see models.py - no UniqueConstraint/index unique, and no alembic migration adds one) and create_correspondence (service.py:44-64) does NOT wrap the insert in an IntegrityError retry loop the way rfi/submittals/transmittals do. This is the only document/comms numbering path lacking the unique-constraint + retry hardening the sibling modules all have (compare rfi/repository.py:next_rfi_number which casts numeric suffixes and rfi/service.py:150-230 retry, and submittals/repository.py:64-102 which parses digits in Python).
- Evidence: repository.py:44 `stmt = select(func.max(Correspondence.reference_number)).where(...)` then `numeric = int(max_number.split('-',1)[1]); return f"COR-{numeric+1:03d}"`. models.py:26 `reference_number: Mapped[str] = mapped_column(String(50), nullable=False)` with no unique=True and no UniqueConstraint in __table_args__. service.py create_correspondence calls repo.create with no try/except IntegrityError.
- Fix: Add a UniqueConstraint(project_id, reference_number) via migration, parse the numeric suffix and take MAX in Python (like submittals next_submittal_number) instead of a lexical string MAX, and wrap create in the same IntegrityError-retry loop used by rfi/submittals/transmittals so a collision re-rolls the number instead of silently writing a duplicate.
